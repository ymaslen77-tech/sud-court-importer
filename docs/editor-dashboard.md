# Редакционный кабинет: безопасная локальная конфигурация

## Состояние

На `/editor` создан отдельный **служебный** доступ, который по умолчанию выключен.
После включения сайт запрашивает HTTP Basic-авторизацию (браузерное окно),
затем показывает `/editor/dashboard` со следующими показателями из реальной PostgreSQL:

- опубликованные и устаревшие карточки судов;
- очередь изменений: источники/контакты, назначения, наблюдения о судьях, судебные дела;
- включённые проверки официальных страниц, ошибки и просроченные проверки;
- число опубликованных судов по регионам.

В кабинете доступно рассмотрение/игнорирование трёх видов технических сигналов:
изменение списка судей, отличие двух снимков реестра судов и изменение
отслеживаемой официальной страницы. Это не подтверждает факт назначения,
изменения адреса или закрытия суда и не меняет опубликованные сведения.
Утверждение фактов и публикация по-прежнему выполняются через контролируемые
CLI-инструменты с проверкой источника и журналом решений.

## Безопасное включение

Доступ недоступен без всех четырёх переменных окружения:

```env
EDITOR_DASHBOARD_ENABLED=true
EDITOR_USERNAME=<separate-editor-login>
EDITOR_PASSWORD=<random-password-at-least-16-characters>
EDITOR_API_TOKEN=<random-token-at-least-32-characters>
```

Не копируйте эти примеры как реальные значения. Сгенерируйте секреты
локальным криптографическим генератором. Храните их в `.env` на хосте
(файл не должен попасть в Git) или в защищённом хранилище секретов.

В Windows PowerShell (из корня проекта) можно создать секреты средствами .NET:

```powershell
$bytes = [byte[]]::new(48)
[System.Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
[Convert]::ToBase64String($bytes)
```

Это демонстрация генерации одного секрета. Для пароля и API-токена
сгенерируйте **два независимых** значения. Учётная запись редактора не должна
совпадать с учётной записью администратора ОС/БД.

Пересоздайте API и веб-контейнеры:

```powershell
docker compose -f compose.local.yaml up -d --force-recreate --wait api web
```

После этого откройте `http://localhost:4173/editor`.
По умолчанию при отсутствии переменных возвращается 404, внутренний
`/api/v1/internal/editor/overview` возвращает 401.

**Нельзя публиковать Basic-аутентификацию через открытый HTTP.**
На публичном хосте требуется HTTPS, внешний authentication proxy
с MFA и ограничением по IP/VPN, аудит доступа и rate limiting.
Предложенный механизм предназначен для локального администратора и
предварительных проверок, не для готового публичного multi-user CMS.

Внутренний API защищён отдельным bearer token, который передаётся
`web -> api` на серверной стороне и не включается в браузерный JavaScript.
Внешний маршрут для этих данных отключён при отсутствии сильного токена.

## Проверки

В CI отдельные запросы удостоверяют, что:
- неавторизованный кабинет возвращает 404 в выключенном состоянии;
- внутренний API без токена возвращает 401;
- при настройке переменных доступ появляется только после проверки учётных данных;
- `/editor/dashboard` содержит метрики и `noindex`;
- разрешены только рассмотрение/игнорирование сигналов, без утверждения новых фактов;
- токены форм привязаны к записи **и типу очереди**, а не только к идентификатору;
- ошибки авторизации, чужой Origin, повторные решения и перепутанный тип очереди отклоняются.

## Следующие действия для полноценного кабинета

1. Управляемые редакторские роли/2FA/аудит входов через внешний IdP.
2. Развитие карточек предложенных изменений и поддержка редакционного workflow для остальных очередей.
3. Отдельное двухэтапное approval-действие **для публикации фактов** со значимыми подтверждениями
   через авторизованные POST endpoints, CSRF-защитой и конфликт-контролем.
4. Журнал принятых решений, ошибки источников, уведомления.
5. Периодический отчёт о региональном покрытии и сроках повторной сверки.

Нельзя считать наличие технической страницы завершением массового наполнения
судов или запуском круглосуточного официального источника.


## Рассмотрение расхождений в кадровых списках (пилот)

После миграции `010_court_staff_roster_diffs.sql` модуль `importer/roster_diff.py`
сравнивает два ранее сохранённых снимка одной официальной страницы состава судей.
Новые изменения автоматически **не** приводят к записи о назначении,
увольнении или публикации.

Новая разрешённая офлайн-выгрузка, принятая через `roster.py stage`, автоматически
передаётся для сравнения с предыдущим сохранённым снимком того же источника.
Для повторной или внеочередной постановки разницы вручную:

```powershell
docker compose -f compose.local.yaml run --rm --entrypoint python importer /work/importer/roster_diff.py queue --older-batch 1 --newer-batch 2
```

В `/editor/dashboard` отображаются как количество кадровых расхождений,
так и конкретные сигналы с официальными ссылками. После проверки редактор
может отметить сигнал как «рассмотрен» или «игнорировать», поставив
галочку подтверждения. Эта операция меняет только
`court_staff_roster_diff_items.review_status`, `reviewed_by` и
`reviewed_at`. Она **не меняет** публичные `courts`,
`judges` или `judicial_appointments`.

POST-обработчик защищён Basic-аутентификацией, проверкой Origin,
короткоживущим токеном формы и внутренним Bearer-токеном.
Повторное рассмотрение элемента (не pending) запрещено.
Настоящие публикации назначений остаются под независимым
ручным утверждением через `importer/judges.py`.

Не используйте Basic-доступ через открытый HTTP. До production
требуются внешний IdP/MFA, разграничение ролей, аудит авторизаций
и ограничения частоты запросов. Наличие этой функции не закрывает
всю систему редакционной проверки.

## Рассмотрение изменений реестров и официальных страниц

Сигналы `registry_diffs` и `source_changes` доступны рядом с `staff_roster_diffs`.
Они содержат ссылку на официальный первоисточник и время наблюдения.
Нажатие «Сигнал рассмотрен» не изменяет таблицу `courts` и не означает, что
новый телефон, адрес или должность проверены. Любое подтверждение конкретного
публичного поля требует независимой редакционной операции через
`importer/profile.py approve` или другой специализированный инструмент
с актуальным документом и подтверждением условий использования.

Рассмотрение сохраняет `reviewed_by`, `reviewed_at` и статус записи.
Разрешены только `staff_roster_diffs`, `registry_diffs`, `source_changes`;
подмена вида очереди, повторное рассмотрение и неавторизованные запросы
отклоняются. Номер записи без вида очереди больше не является достаточным
основанием для подтверждения формы. Для production необходимы IdP/MFA,
административный аудит и отдельная приёмка защиты.
