# Редакционный кабинет: безопасная локальная конфигурация

## Состояние

На `/editor` создан отдельный **служебный** доступ, который по умолчанию выключен.
После включения сайт запрашивает HTTP Basic-авторизацию (браузерное окно),
затем показывает `/editor/dashboard` со следующими показателями из реальной PostgreSQL:

- опубликованные и устаревшие карточки судов;
- очередь изменений: источники/контакты, назначения, наблюдения о судьях, судебные дела;
- включённые проверки официальных страниц, ошибки и просроченные проверки;
- число опубликованных судов по регионам.

Никаких функций подтверждения/изменения прямо в кабинете пока нет.
Редакционный процесс утверждения через контролируемые CLI-инструменты
сохраняет обязательную проверку источника и журнал аудита.

## Безопасное включение

Доступ недоступен без всех четырёх переменных окружения:

```env
EDITOR_DASHBOARD_ENABLED=true
EDITOR_USERNAME=<separate-editor-login>
EDITOR_PASSWORD=<random-password-at-least-16-characters>
EDITOR_API_TOKEN=<random-token-at-least-32-characters>
```

Не копируйте эти примеры как реальные значения. Сгенерируйте секреты
локальным криптографическим генератором. Храните их в `.env` на хосте
(файл не должен попасть в Git) или в защищённом хранилище секретов.

В Windows PowerShell (из корня проекта) можно создать секреты средствами .NET:

```powershell
$bytes = [byte[]]::new(48)
[System.Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
[Convert]::ToBase64String($bytes)
```

Это демонстрация генерации одного секрета. Для пароля и API-токена
сгенерируйте **два независимых** значения. Учётная запись редактора не должна
совпадать с учётной записью администратора ОС/БД.

Пересоздайте API и веб-контейнеры:

```powershell
docker compose -f compose.local.yaml up -d --force-recreate --wait api web
```

После этого откройте `http://localhost:4173/editor`.
По умолчанию при отсутствии переменных возвращается 404, внутренний
`/api/v1/internal/editor/overview` возвращает 401.

**Нельзя публиковать Basic-аутентификацию через открытый HTTP.**
На публичном хосте требуется HTTPS, внешний authentication proxy
с MFA и ограничением по IP/VPN, аудит доступа и rate limiting.
Предложенный механизм предназначен для локального администратора и
предварительных проверок, не для готового публичного multi-user CMS.

Внутренний API защищён отдельным bearer token, который передаётся
`web -> api` на серверной стороне и не включается в браузерный JavaScript.
Внешний маршрут для этих данных отключён при отсутствии сильного токена.

## Проверки

В CI отдельные запросы удостоверяют, что:
- неавторизованный кабинет возвращает 404 в выключенном состоянии;
- внутренний API без токена возвращает 401;
- при настройке переменных доступ появляется только после проверки учётных данных;
- `/editor/dashboard` содержит метрики и `noindex`;
- исполняется только чтение, не происходит автоматического утверждения данных.

## Следующие действия для полноценного кабинета

1. Управляемые редакторские роли/2FA/аудит входов через внешний IdP.
2. Отображение *самих* карточек предложенных изменений, с проверяемыми источниками.
3. Отдельное двухэтапное approval-действие со значимыми подтверждениями
   через авторизованные POST endpoints, CSRF-защитой и конфликт-контролем.
4. Журнал принятых решений, ошибки источников, уведомления.
5. Периодический отчёт о региональном покрытии и сроках повторной сверки.

Нельзя считать наличие технической страницы завершением массового наполнения
судов или запуском круглосуточного официального источника.
