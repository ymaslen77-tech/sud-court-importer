# Готовность к промышленной эксплуатации: обязательные проверки

**Текущее состояние (15.10.2026):** публичный пилот Next.js на Vercel, отдельный NestJS API и база Neon PostgreSQL/PostGIS **развёрнуты и подключены**. В Neon применены 13 миграций, загружены 273 предварительные записи, но **0 судебных карточек редакционно утверждены**. Это **не** означает завершённую промышленную эксплуатацию: staging-окружение, приёмка, безопасность редактора, мониторинг, восстановление и полностью управляемый CD ещё требуют реализации. Новые функции выбора видов судов и поиска по адресу находятся в рабочей ветке GitHub; перед утверждением их доступности в production необходимо проверить соответствующий Vercel deployment и его SHA.

**Основной стандарт:** [Полная схема разработки, размещения и работы сайта](site-development-deployment-architecture.md).  
**Подробный операционный регламент:** [Development → GitHub → Actions → Vercel ↔ Neon](development-deployment-architecture.md).

**Локальный Docker Compose** (`compose.local.yaml`) использует тестовые локальные credentials и dev-серверы. Его нельзя размещать в публичном интернете как production-сервис.

## Контрольные точки перед переходом от пилота к полноценной эксплуатации

1. Подтвердить права доступа к двум существующим Vercel-проектам и рабочей Neon PostgreSQL, inventory сервисов и секретов. Собственный домен подключить, если он принят владельцем; не хранить секреты в Git.
2. Сборки `next build` и NestJS production mode, ingress с HTTPS и HSTS, закрытая PostgreSQL сеть, `DATABASE_URL` через secret manager, раздельные права БД (read-only API vs редактор/импортёр), health checks и ресурсные лимиты.
3. Обоснованный DPIA/обработка персональных данных, политика конфиденциальности, редакционная процедура; источники судебных актов и кадровая информация требуют отдельной проверки прав и применимого законодательства.
4. Выгрузки официальных данных только через разрешённые каналы, fail-closed robots/terms, журнал загрузок и обновлений, возраст записи и флаг stale. Ни один непроверенный источник не включает автоматическую публикацию.
5. Каждый день: проверяемые резервные копии PostgreSQL (шифрование, вне сервера) и исходных лицензированных медиа; отдельно испытанное восстановление на чистом контейнере.
6. Постоянный процесс intake и watch с мониторингом очереди: задержка получения, ошибки источников, непросмотренные изменения, SLA на телефон/часы/назначения.
7. SEO перед индексацией: базовый hostname, canonical, sitemap shards при >5000 судах, отсутствие случайных noindex, ссылки на официальные источники, отсутствие тонких автоматически сгенерированных страниц.
8. A11y проверка, нагрузочный тест на собственном staging, внешний security review, интеграционный smoke, контроль API rate limits, CSP, журнал отказов, алерты.
9. Выпуск только после регистрации acceptance: фактическое число проверенных карточек, региональное покрытие по подтверждённому эталону, freshness distribution, фото с действующей лицензией, обоснованные правки в судебных назначениях.

## Что нужно получить перед этапом

- Доступный production-хостинг/сервер и домен (или разрешение на выбранную инфраструктуру).
- Правила и форматы получения официальных данных; разрешение на регулярное обновление и повторное использование.
- Утверждённые требования к защите персональных данных и ответственное лицо, проверяющее судебные назначения.

До выполнения пунктов выше **не переводить Draft PR в main и не объявлять промышленную эксплуатацию, достоверность карточек или безопасность редактора завершёнными**. Публичный справочный пилот уже развёрнут.

Для разработки на Windows безопасный updater: `scripts/safe-update-local.ps1`, который сохраняет дамп PostgreSQL и исходники до обновления. Его нельзя считать production backup policy.
