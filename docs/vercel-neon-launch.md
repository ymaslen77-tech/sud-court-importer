# Развёртывание «Суды России» на Vercel + Neon

Дата: 14 октября 2026. Эта инструкция описывает фактические два Vercel-проекта и оставшийся внешний шаг подключения базы. **Ни одна неподтверждённая карточка не публикуется автоматически.**

## Развёрнутые приложения

| Компонент | Vercel | Домен | Состояние |
| --- | --- | --- | --- |
| Next.js (из `apps/web`) | `sudy-rossii` | https://sudy-rossii.vercel.app | Сборка production READY; предварительный каталог работает без API |
| NestJS (из `apps/api`) | `sudy-rossii-api` | https://sudy-rossii-api.vercel.app | Сборка production READY; для запросов к данным нужна PostgreSQL |
| PostgreSQL/PostGIS | Neon | Нет подтверждённой подключённой базы в этом проекте на момент подготовки | Требует создания БД и безопасного применения миграций |

## Вариант A: публичный справочный пилот без БД

Не устанавливать `API_URL` для Next.js. Приложение показывает 151 **предварительную** карточку из сохранённых источников, с предупреждением и `noindex`. Подтверждённый реестр остаётся пустым; реальные сведения о судьях или судебных актах не изобретаются.

Проверить:

- `/`, `/courts`, `/courts/coverage`
- `/courts/region-54/sud-54rs0012`, `/courts/region-55/sud-55os0000`
- `/courts/region-27/sud-27ms0001`, `/search?q=54RS0012`
- `/api/status`: JSON с `verified_backend_configured=false` и `preliminary_records=151`
- `/sitemap.xml` не должен содержать 151 исследовательский URL.

Production-адрес открыт без требуемой Vercel Authentication; preview остаётся под защитой.

## Вариант B: полноценный редакционно управляемый реестр

1. Создать PostgreSQL 16+ с поддержкой PostGIS в Neon. Подключение исключительно через защищённые переменные окружения, не сохранять URI в GitHub.
2. Выполнить миграции на **новой пустой** БД из доверенного окружения:

   ```bash
   python importer/migrate.py --list
   python importer/migrate.py --check
   python importer/migrate.py --apply --confirm
   python importer/migrate.py --check
   ```

   `DATABASE_URL` должен быть установлен в окружении; не печатать его значение, не загружать в issue/логи. Проверки контрольных сумм препятствуют тихой подмене уже применённых SQL-файлов. Схема миграций создаёт только структуры, не публичные карточки.

3. Установить в проекте `sudy-rossii-api` защищённый `DATABASE_URL` для production, а `WEB_ORIGIN=https://sudy-rossii.vercel.app`. Повторно развернуть API.
4. Проверить `https://sudy-rossii-api.vercel.app/api/v1/health`: только реальный ответ `200 {"status":"ok","database":"reachable"}` подтверждает подключение. Наличие статуса Vercel `READY` не доказывает готовности БД.
5. Установить в `sudy-rossii` переменную `API_URL=https://sudy-rossii-api.vercel.app`, заново развернуть Next.js, проверить списки судов и editor API.
6. Закрыть редактор: создать отдельно устойчивые случайные учётные данные `EDITOR_USERNAME`, `EDITOR_PASSWORD`, `EDITOR_API_TOKEN`, включить кабинет только после ручной проверки безопасной авторизации и HTTPS. Никогда не публиковать токены, пароли или URI в репозитории.
7. Данные из `importer/seeds/*unreviewed*` передавать через существующий offline intake → staging → ручная пофактовая приёмка. Никогда не переводить 151 карточку в verified массовым SQL.

## Состояние обязательных проверок

- GitHub CI: тесты импортёра, TypeScript сборка, Docker smoke, проверка отсутствия исследования в sitemap.
- API health: включает проверку реальной БД; без `DATABASE_URL` возвращает 503, а не ложный OK.
- Миграции: отдельная блокировка `pg_advisory_lock`, каждая миграция транзакционная, контроль SHA-256 и порядка; повторный запуск безопасен при той же версии SQL.
- Backup и восстановление Neon: проверить отдельно через интерфейс провайдера перед фактической массовой публикацией.
- Мониторинг: настроить логирование ошибок, тест доступности и регулярный контроль только после включения production БД.
- **Не включать автоматический краулинг источников:** пользователь поручил работать вручную с открытыми материалами.
