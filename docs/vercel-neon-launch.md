## Проверка работающего окружения

1. Открыть https://sudy-rossii.vercel.app и проверить страницу каталога, поиск и доступность HTTPS.
2. Проверить https://sudy-rossii-api.vercel.app/api/v1/health: ответ `200` с `{"status":"ok","database":"reachable"}` подтверждает фактическую доступность БД (а не только READY в панели Vercel).
3. Проверить `/api/status` сайта: сведения о предварительных записях и количестве `verified` должны быть разделены. До выкладки последнего Next.js-кода контракт ответа может отличаться — уточнять текущий **deployment SHA**.
4. Проверить, что `/sitemap.xml` не содержит предварительные карточки, а сами карточки имеют `noindex`.
5. Проверить GitHub Actions на **том же commit SHA**, который собирается в Vercel. Зеленый CI другой версии недостаточен.

## Переменные окружения

| Vercel-проект | Переменная | Назначение и защита |
| --- | --- | --- |
| `sudy-rossii` | `PUBLIC_SITE_URL` | Публичный HTTPS URL для canonical/metadata |
| `sudy-rossii` | `API_URL` | `https://sudy-rossii-api.vercel.app`; только серверная настройка Next.js |
| `sudy-rossii-api` | `DATABASE_URL` | Приватная Neon PostgreSQL URI; хранить только как защищённую production-переменную |
| `sudy-rossii-api` | `WEB_ORIGIN` | Разрешённый источник браузерных обращений: `https://sudy-rossii.vercel.app` |
| редактор/авторизация | отдельные секреты | Не включать редакционный кабинет в production до проверки прав, авторизации и защиты от злоупотреблений |

Не публиковать URI БД, пароли, токены и .env в PR, логи и документацию. Preview **не должен** иметь доступ к боевой строке подключения.

## Безопасный выпуск новой версии

1. Создать новую ветку, подготовить PR, пройти CI и ревью. Пользовательские данные и судебные источники проходят отдельную юридическую приёмку.
2. Создать/проверить Preview Deployment с отдельным окружением, не использовать production Neon. Прогнать smoke и SEO.
3. Проверить миграции на отдельной staging-ветке Neon, наличие backup и контроль SHA-256 исходных SQL. На действующей базе скрипт `importer/migrate.py --check` должен фиксировать текущую историю.
4. Для совместимой миграции расширения — сначала безопасно обновить БД, затем приложение; destructive/contract — отдельным последующим этапом. Миграции не запускать неявно из каждого запроса.
5. После разрешённого merge в `main` развернуть production, проверить API health, сайт, карточки, sitemap и редакторские функции.
6. Контролировать алерты и ошибки. При необходимости вернуть предыдущий Vercel deployment; восстановление данных Neon выполняется отдельно по заранее проверенной процедуре.

### Ограничения публикации

Последняя попытка выкладки нового Next.js-кода была ограничена суточной квотой Vercel Hobby (`402 payment_required`). Это состояние **может измениться**: перед повторным деплоем проверять текущий тариф/квоту. Не обходить квоту созданием случайного нового проекта или подменой окружения. Не заявлять, что последнее изменение GitHub уже находится в production, пока не проверены deployment ID, SHA и реальные HTTP-ответы.

Автоматический регулярный сбор с судебных сайтов ранее отложен. Для его включения необходимо отдельное разрешение, подтверждённые условия источника, worker, защищённый планировщик, аудит данных и процедура ручного утверждения. Миграции БД и CI можно автоматизировать **отдельно от** массового сбора судебных сведений.

## Работа с уже загруженными сведениями

- 273 предварительные строки существуют в рабочей PostgreSQL, но **не в публичной таблице `courts`**. Наличие таблиц с очередями в production — не то же самое, что собственная staging branch Neon.
- Каждая запись проходит проверку идентификатора, типа суда, географической подсудности, адреса, контактов, первоисточника, даты актуальности и прав на использование.
- До редакционного `approve` сохранять `pending` и `noindex`; не выполнять массовую установку `verified`.
- Зафиксированное состояние загрузки: [журнал Neon](./neon-court-staging-2026-10-14.md); юридические ограничения: [приёмка](./acceptance-status.md).

## Резервирование и защита

Перед существенными изменениями проверить копию БД и **практический сценарий восстановления**. Сам факт наличия веток Neon не заменяет независимые backups. Отдельно необходимы ограничение ролей DB, защищённый редакторский API, наблюдаемость и уведомления о недоступности сайта или БД. Файловые вложения и большие PDF при появлении соответствующей функции размещать в отдельном S3-совместимом хранилище с политиками доступа, а не на диске бессостоящего веб-приложения.
