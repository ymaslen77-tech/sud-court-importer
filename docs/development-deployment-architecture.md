# Полная схема разработки, размещения и работы сайта «Суды России»

**Статус документа:** утверждённая целевая инфраструктурная схема проекта, редакция 1.0 от 15.10.2026.  
**Область действия:** репозиторий `ymaslen77-tech/sud-court-importer`, web-приложение, API, база данных, редакционные и фоновые процессы.  
**Важно:** ниже отдельно указано, что уже реально работает, а что является стандартом для последующих этапов. Наличие компонента в этой схеме не означает, что он уже настроен.

## 1. Полная цепочка разработки и работы

| № | Уровень | Назначение | Технология / размещение |
| --- | --- | --- | --- |
| 1 | **Локальная разработка** | Создание и изменение сайта, API и моделей данных; ручная проверка, тесты, локальные миграции | Windows / Git / pnpm / Docker Compose; localhost |
| 2 | **GitHub — репозиторий** | Единый источник кода и документации, история изменений, ветки, Pull Requests, code review | `ymaslen77-tech/sud-court-importer` |
| 3 | **GitHub Actions — CI/CD** | Статические проверки, сборка, тесты, security gates, проверка миграций и запрет публикации при провале CI | `.github/workflows/`; CD в production — только по утверждённым правилам |
| 4 | **Vercel — основной хостинг** | Публичные HTTPS-страницы, Next.js, SSR, API Routes, серверный рендеринг; отдельно размещён NestJS API | Проекты `sudy-rossii` и `sudy-rossii-api` |
| 5 | **Neon — PostgreSQL** | Таблицы, регионы, суды, источники, пользователи (по мере создания), редакционные очереди, транзакции; PostGIS | PostgreSQL 16, база `courts`, проект `sudy-rossii` |
| 6 | **Домен + DNS** | Постоянный публичный адрес, маршрутизация на Vercel, сертификаты HTTPS, канонические URL | Сейчас `sudy-rossii.vercel.app`; собственный домен и DNS — отдельный этап |
| 7 | **Пользователи сайта** | Открывают страницы, ищут суды и судебные сведения, пользуются сервисами; по мере готовности — регистрация и персональные функции | Браузер → домен → Vercel → серверный API → Neon |

### Архитектура

```text
РАЗРАБОТКА И ПУБЛИКАЦИЯ
Локальная разработка
    ↓
GitHub (ветка → Pull Request → review)
    ↓
GitHub Actions (lint/check → tests → build → smoke → security gates)
    ↓
Vercel Preview (без использования production-секретов и данных)
    ↕
Neon staging branch (отдельная, обезличенная и ограниченная по доступу БД)
    ↓
Одобренный merge в main
    ↓
Vercel Production (Next.js + отдельный NestJS API)
    ↕
Neon Production (PostgreSQL/PostGIS)
    ↓
Monitoring / rollback / восстановление БД по отдельной процедуре

ПОЛЬЗОВАТЕЛЬСКИЙ ТРАФИК
Посетитель → Домен + DNS + HTTPS → Vercel (Next.js / SSR / API Routes)
                                       ↓
                                 NestJS API на Vercel
                                       ↓
                              Neon PostgreSQL + PostGIS
```

Preview и staging не должны изменять production-таблицы или получать production-ключи. Стрелка `CI → Production` является **целевым автоматизированным порядком**, а не подтверждением, что CD по `main` уже включён.

## 2. Дополнительные компоненты инфраструктуры

| Компонент | Назначение | Планируемое размещение | Текущий статус |
| --- | --- | --- | --- |
| **Фоновые задачи** | Длительные процессы, синхронизация разрешённых данных, обработка очередей, изображения и документы | Отдельный worker/очередь; Neon — хранилище состояния. Возможность использования Neon Functions оценивается отдельно | Постоянный production worker не введён |
| **Планировщик** | Регулярные задания, контроль свежести, отчёты и обновления | Vercel Cron как триггер короткой задачи либо внешний scheduler + worker; Neon хранит состояние/блокировки | Production cron не подтверждён |
| **Файловое хранилище** | PDF, изображения, фотографии, приложения и лицензированные вложения | S3-совместимое объектное хранилище, ссылки и метаданные в Neon | Отдельное production-хранилище не подтверждено |
| **Авторизация** | Регистрация, вход, сессии, роли посетителя и редактора | Приложение и Neon; Neon Auth — возможный вариант после архитектурного решения | Полноценная публичная auth/role-система не введена; редактор требует отдельной защиты |
| **Мониторинг** | Доступность, журналы ошибок, производительность, тревоги, состояние фоновых очередей | Vercel logs/observability + внешний мониторинг | CI и выборочные проверки доступности реализованы; полноценные алерты и SLA — впереди |
| **Резервное копирование** | Восстановление БД и критических файлов при потере данных, ошибке миграции | Возможности восстановления Neon + независимые зашифрованные резервные копии и restore drill | Политика и тест восстановления production не подтверждены |
| **Защита** | HTTPS, хранение секретов, разграничение прав, аудит, API rate limits, защита кабинета | Vercel, приложение, Neon, WAF/лимиты при необходимости | HTTPS и секреты окружения применяются; остальные меры требуют security-приёмки |

Длинные/ресурсоёмкие фоновые процессы **не запускать внутри обычного HTTP-запроса Vercel** как замену worker. Запуск расписания не должен приводить к бесконтрольному сбору открытых сайтов: используем только разрешённые источники и зафиксированные правила доступа.

## 3. Стандарт работы и публикации — 10 этапов

1. **Development.** Разработка локально. Запуск Next.js/NestJS/PostgreSQL в Docker Compose, проверка типов, тесты, пробная миграция на изолированной БД.
2. **GitHub Branch.** Каждую задачу вести в отдельной ветке; не изменять `main` напрямую. Коммитить код, миграции, документацию и тесты; не коммитить секреты или личные данные пользователей.
3. **Pull Request.** Обязательная проверка GitHub Actions, осмотр изменений и оценка рисков. Не принимать PR при красном CI или непроверенных миграциях.
4. **Preview Deployment.** Создать отдельную предварительную версию на Vercel из PR; закрыть её от несанкционированного доступа, не подключать к рабочей БД.
5. **Staging Database.** Подключить отдельную Neon-ветку/БД для интеграционных тестов и миграций. Использовать синтетические или разрешённые обезличенные данные; проверить полную схему и последствия миграции.
6. **Merge в main.** Объединять только после зелёных тестов, ревью и подтверждённой совместимости web/API/DB. Завершённость отдельной задачи не означает автоматического одобрения всей базы судов.
7. **Production Deployment.** CD запускает Vercel production из утверждённого `main`; веб-приложение и API обновляются контролируемо, с проверкой окружения и секретов.
8. **Database Migrations.** Производственная схема меняется отдельным **контролируемым шагом** с чек-суммами, резервной точкой и планом отката. Порядок относительно пункта 7 выбирается по совместимости релиза: часто безопасная расширяющая миграция **до** переключения API, удаление старых колонок — только после обновления всех клиентов. Нельзя автоматически выполнять непроверенный SQL из каждого PR.
9. **Monitoring.** После релиза проверить HTTPS, маршруты, поиск, `/api/v1/health`, логи web/API, нагрузку Neon, права доступа, наличие подтверждённых и непроверенных записей в отдельных выдачах; включить наблюдение и алерты.
10. **Rollback.** При проблемах вернуть предыдущую исправную версию Vercel; если изменилась БД, использовать отдельный совместимый rollback/restore plan, а не рассчитывать, что откат кода отменит миграции или изменения данных.

**Запрещённая практика:** запускать DDL-миграции при каждом холодном старте serverless-функции; использовать production Neon для тестирования PR; объединять ветку в `main` при неуспешном CI или без проверки источников судебных сведений.

## 4. Распределение ответственности

| Система | Ответственность | Что не является её функцией |
| --- | --- | --- |
| **GitHub** | Код, документация, Pull Requests, ревью, история и правила ветвления | Не хостит работающий Next.js/API и не является БД |
| **GitHub Actions** | Проверка качества, тесты, статус PR; в целевой схеме — разрешённые триггеры развёртывания | Не заменяет тестовое окружение, production-администрирование и редакционную проверку судов |
| **Vercel** | Публичный веб-хостинг, SSR, Next.js API Routes, выполнение NestJS API, HTTPS, preview/production | Не заменяет долгоживущий worker и PostgreSQL |
| **Neon** | PostgreSQL/PostGIS, ветки БД, данные, транзакции, связи, доступ через роли | Не заменяет хостинг сайта, DNS и файловое хранилище |
| **Домен и DNS** | Публичное имя и направление HTTPS-трафика на хостинг | Не хранят код и содержимое базы |
| **Приложение** | Бизнес-логика, роли, проверка источников, фильтрация и безопасная выдача данных | Не имеет права объявлять предварительные записи подтверждёнными |
| **Администратор / редактор** | Контроль доступов, бюджетов и лимитов, приёмка релизов, пофактовое одобрение судебных сведений | Не должен передавать секреты в PR, логи или публичный чат |

### Разделение сред и источников данных

- **Local:** Docker Compose, изолированные localhost-порты, локальная тестовая БД; не использовать её тестовые пароли в облаке.
- **Preview / staging (целевое правило):** тестовая сборка Vercel + Neon staging; отдельные секреты и обезличенные данные; не отправлять туда реальные пользовательские обращения.
- **Production:** два Vercel-сервиса + Neon `courts`; доступ только по HTTPS, настройки в environment secrets.
- **Исследовательские записи:** никогда не считать `pending` подтверждением действующего суда. До пофактовой редакционной приёмки они не участвуют в проверенном поиске или sitemap и имеют `noindex`.
- **Миграции:** файлы `db/migrations/*.sql`, контролируемый инструмент `importer/migrate.py`. Утверждение релиза, изменение схемы и утверждение юридических данных — **три разных решения**.

## 6. Минимальные критерии готовности к промышленной эксплуатации

- CI и production build проходят; production развёртывание из `main` воспроизводимо, а Preview не имеет права писать в production.
- Staging Neon отдельная; миграции проверены и применены с воспроизводимым журналом и восстановлением на тестовой ветке.
- Секреты и роли разделены; кабинет редактора защищён, вход и аудит протестированы; ненужные публичные endpoints закрыты.
- Есть внешний мониторинг, предупреждения об ошибках, проверенные резервные копии и практика восстановления.
- Приобретённый пользовательский домен корректно настроен (если принят к запуску), канонические ссылки и HTTPS проверены.
- Реальные судебные сведения подтверждены по индивидуальным официальным первоисточникам с датой проверки и правовым основанием публикации; неподтверждённые сведения остаются вне индекса.
- Подготовлен план развёртывания и отката кода **и отдельно данных**, а также лицо, принимающее релиз.

## Итоговая архитектура

```text
Разработка → GitHub → GitHub Actions → Vercel ↔ Neon
Пользователь → Домен/DNS → Vercel → Серверная логика → Neon
```

**Это целевой стандарт промышленной эксплуатации** с автоматическим развёртыванием, контролем изменений, разделёнными средами, мониторингом, защитой и восстановлением. Реализованные компоненты и незакрытые задачи указаны выше; не подменять целевой стандарт утверждением о полной готовности production.
