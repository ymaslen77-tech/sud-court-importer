# Сверка изменений в списках судей — этап разработки

## Зафиксированная граница достоверности

Отдельные официальные снимки состава судей могут содержать изменения ФИО, должности, кабинета, телефона, реквизитов указа. Исчезновение из списка **не является доказательством увольнения**, появление не является доказательством назначения. Совпадение ФИО не доказывает тождество личности. Публикация только после независимой редакционной проверки.

## Технический контракт реализации

1. Хранить два снимка одного `source_id` и `official_court_url`; отклонять сравнение разных судов и источников.
2. Сравнивать полную пару ФИО + указанная должность; создавать события `first_listed`, `no_longer_listed`, `field_changed`. Предположительное `position_changed` возможно только при единственном ФИО в каждом снимке и всегда требует ручной проверки.
3. В БД отдельные `court_staff_roster_diff_runs` и `court_staff_roster_diff_items` с уникальными парами batch ID, статусами pending/reviewed/ignored и журналом reviewer/timestamp.
4. Не изменять публичные `courts`, `judges` или `judicial_appointments` через автоматический diff и acknowledgement.
5. Нужны unit-тесты на повторы, пропажу ФИО, новую должность, изменение контактов, пустой неполный список, неоднозначные совпадения, перезапуск без дублей. Нужны Docker/PostgreSQL smoke и миграция в Windows updater.
6. Новые очереди учитывать в `importer/coverage.py` и fail-closed `importer/readiness.py`.

## Статус

Документ определяет задачи, но **не подтверждает их реализацию**. Производственное применение запрещено до прохождения автоматических тестов, проверки миграций и приёмки редакторского workflow.

## Другие блокеры выпуска

Массовые легальные источники по всем субъектам и видам судов РФ, независимая верификация карточек, лицензированные реальные фото, проверенные координаты, законный канал судебной практики, production HTTPS, резервное восстановление и мониторинг должны иметь отдельные доказательства. Успешный CI не закрывает эти блокеры.
